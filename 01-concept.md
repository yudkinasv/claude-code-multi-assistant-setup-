# 1. Концепция

## Проблема, которую решает многоассистентная оргструктура

Когда работа с Claude Code становится плотной, появляются ловушки:

**Ловушка №1. Перегруз контекста.** Один длинный чат, в котором обсуждается и стратегия проекта, и операционные мелочи, и инфраструктура, и интеграции — рано или поздно теряет связность. Модель помнит фрагменты, но смешивает их. Качество ответов падает.

**Ловушка №2. Размытая роль.** Если один и тот же ассистент сегодня пишет тебе слоганы для бренда, завтра помогает с git-конфликтами, послезавтра напоминает позвонить юристу — у него **нет фокуса**. Он отвечает «всем сразу», и в каждой зоне даёт не лучший результат.

**Ловушка №3. Параллельные проекты сливаются в кашу.** Если у тебя три бренда (или три клиента, или три направления жизни) — в одном чате этому невозможно вести последовательную работу. Ты сама забываешь, что обсуждали по проекту А, когда переключилась на проект Б.

**Ловушка №4. Внешние сервисы остаются за бортом.** Claude Code умеет читать файлы и выполнять команды, но он не знает про твой Google Calendar, твой Notion, твой планировщик задач. Все эти системы живут отдельно. Ассистент в Code не помнит, что ты только что отметила задачу выполненной в Todoist.

---

## Решение: разделение труда между ассистентами

Вместо одного «универсала» — **команда специализированных ассистентов**, каждый в своей зоне. Они:
- Имеют узкую роль и понятный круг обязанностей.
- Живут в отдельных рабочих папках со своей memory.
- Общаются между собой через **файловые каналы** (один пишет в файл — другой читает).
- Один из них (координатор) выступает «мостом» к внешнему миру через REST API.

Это не магия — это применение классических принципов разделения труда из управления командами к ИИ-ассистентам.

---

## Принципы, на которых это работает

### 1. У каждого ассистента — узкая роль и явные «не-зоны»

Это самое важное. Ассистент должен знать **не только что он делает, но и чего НЕ делает**. Иначе он будет залезать в чужие зоны и портить работу.

Пример из жизни:
- Координатор (общий помощник, видит все проекты) — НЕ пишет тексты. НЕ принимает архитектурные решения. НЕ работает с визуалом.
- Бренд-менеджер — НЕ пишет финальный слоган сам. НЕ редактирует архитектуру бренда. НЕ координирует другие проекты.
- Писатель/копирайтер — НЕ занимается планированием. НЕ интегрируется с внешними API.

Запись «чего НЕ делает» в правилах ассистента — обязательная часть его инструкции.

### 2. Каждый ассистент живёт в своём пространстве

«Своё пространство» — это:
- **Своя папка на диске.** Не пересекается с папками других ассистентов.
- **Свой git-репозиторий** (или своя ветка одного репо — worktree). Свой бэкап на GitHub.
- **Своя memory** в Claude Code. У каждого projectId — своя папка memory.
- **Свой профиль терминала** с автозапуском. Одним кликом ты попадаешь в нужного ассистента.

Это даёт **изоляцию контекста** и **независимость работы**. Перезапуск одного ассистента не влияет на остальных.

### 3. Координация — через файлы, не через chat

В Claude Code невозможно «сказать одному чату что-то так, чтобы услышал другой». Каждая сессия живёт в своей памяти.

Поэтому общение между ассистентами идёт через **файлы-каналы**:
- Ассистент A хочет передать сообщение ассистенту B → пишет в файл `for-B.md` в репо B (или в своей папке для B).
- Ассистент B при следующем заходе читает этот файл.
- Файл лежит на диске, не теряется. Можно листать историю переписки между ассистентами.

Это медленнее живого общения, но **устойчиво**, **воспроизводимо** и **видимо тебе** (ты в любой момент можешь открыть файл и посмотреть, кто что кому передал).

### 4. Связь с внешним миром — через одного координатора

Если каждый из пяти ассистентов будет ходить в Singularity, Notion и Google Calendar — это:
- Пять токенов, пять интеграций, пять зон риска.
- Конфликты, кто-что-где обновил.
- Раздутый allow-list в каждой папке.

Поэтому один ассистент берёт на себя **роль координатора и моста**. Он:
- Имеет токены к внешним сервисам.
- Пишет/читает там по запросу.
- Транслирует во внутреннюю систему через файлы (другие ассистенты узнают про задачи через него).

Один источник правды, один риск.

### 5. Финальное решение — всегда у тебя

Никакой ассистент не имеет права отправлять финальный артефакт (бриф подрядчику, публичный текст, изменение в продакшен) **без явного «да» от тебя**.

Это правило защищает:
- От накопления ошибок (ассистент уверенно пошёл, через 5 итераций ты увидела, что всё мимо).
- От размывания границ роли (если ассистенту дать право финализировать — он начнёт «решать за тебя», даже если не должен).
- От твоего собственного выгорания (когда система делает всё «сама», у тебя теряется ощущение управления).

Финал = человек. Это не баг, это фича.

## Что получаешь на выходе

После настройки многоассистентной оргструктуры:

1. **Вместо одного длинного чата — несколько коротких целевых.** Каждый чат — про свою зону. Контекст не размывается.

2. **Параллельные проекты не сливаются.** У каждого проекта (или направления) — свой ассистент или своя ветка работы. Ты переключаешься между ними одним кликом профиля терминала.

3. **Координация не нагружает тебя.** Координатор-ассистент сам напоминает «у Х для тебя задача», «в Y отметила выполненным эту задачу за день», «по Z висит решение».

4. **Внешние сервисы интегрированы.** Создаваемые в чате задачи попадают в твой планировщик. Отмеченные выполненными там — становятся видимы ассистенту здесь. Не надо дублировать руками.

5. **Воспроизводимо.** Вся конфигурация в файлах + git. Перенесла на другой компьютер — продолжила работать. Случайный сбой Code — после перезапуска всё восстанавливается.

6. **Прозрачно для тебя.** Все взаимодействия — в файлах. Открыла любой канал, увидела что и когда передавалось. Никакой «магии за спиной».

---

## Где это НЕ работает (честно)

- **Если у тебя один проект и простая задача.** Оверкилл — обычного чата хватит.

- **Если ты планируешь использовать Code эпизодически.** Время на сборку оргструктуры (4-8 часов первоначально + 1-2 часа поддержки в неделю) не окупится.

- **Если ты ждёшь полной автоматизации.** Ассистенты могут многое, но финальные решения по содержанию остаются за тобой. Если хочешь чтобы «всё работало без тебя» — это не сюда.

- **Если у тебя нет привычки работать с git и файлами.** Методология сильно опирается на git-операции и структуру папок. Если это для тебя боль — лучше начать с базы.
