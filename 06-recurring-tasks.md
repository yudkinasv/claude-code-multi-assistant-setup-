# 6. Регулярные проверки

В отличие от разовых задач, регулярные проверки нужно делать **с определённой периодичностью** — раз в день, раз в неделю, раз в месяц. Claude Code не имеет встроенного cron-подобного механизма, но это легко имитируется через файл с расписанием и автопроверкой при первом сообщении сессии.

---

## 6.1. Зачем регулярные проверки

Системы с временем приобретают **дрейф** — медленное изменение состояния, которое незаметно изо дня в день, но через месяц становится проблемой:
- Нагрузка на внешний API растёт по мере добавления задач.
- Канал коммуникации между ассистентами засоряется неактуальными сообщениями.
- Memory одного ассистента раздувается ненужными feedback-ами.
- Worktree-ветки накапливают необъединённые наработки.

Регулярные проверки **ловят дрейф рано**, пока он не превратился в кризис.

---

## 6.2. Где живут регулярные проверки

У ассистента, который умеет их вести (обычно — **инфраструктурщик**), в его репо создаётся файл:

`recurring-tasks.md`

В этом файле — список задач периодического характера, каждая с метаданными:
- **Название.**
- **Периодичность** (ежедневно / еженедельно / ежемесячно / разово к дате).
- **Последняя проверка** (YYYY-MM-DD).
- **Следующая проверка не позже** (YYYY-MM-DD).
- **Что делать** (короткое описание процедуры).
- **Когда поднимать тревогу** (что считать «нагрузка вышла за норму»).
- **Что докладывать пользователю.**

Шаблон одной задачи:

```markdown
## <название>

- **Периодичность:** еженедельно
- **Последняя проверка:** 2026-05-14
- **Следующая проверка не позже:** 2026-05-21
- **Что делать:**
  1. <шаг 1>
  2. <шаг 2>
- **Когда поднимать тревогу:**
  - <условие 1> — обсудить с пользователем
- **Что докладывать пользователю:** одной фразой — «<нагрузка>: <показатель>, в норме / нужна оптимизация».
```

---

## 6.3. Правило в CLAUDE.md инфраструктурщика

Раздел в его CLAUDE.md:

> ## Регулярные проверки
>
> При первом сообщении пользователя в каждой моей сессии:
> 1. Прочесть `recurring-tasks.md`.
> 2. Найти задачи, у которых `Следующая проверка не позже` ≤ сегодня.
> 3. Если таких **нет** — молча работать дальше.
> 4. Если есть **одна** — упомянуть пользователю одной строкой: «у меня регулярная проверка просрочена: <название> (последняя — DD-MM-YYYY). Сделать сейчас или позже?».
> 5. Если есть **несколько** — перечислить списком, спросить с чего начать.
>
> После выполнения проверки — обновить в `recurring-tasks.md` поля «Последняя проверка» и «Следующая проверка не позже». Сделать коммит + push.

**Принцип «не запускать без согласия пользователя».** Ассистент сообщает о просрочке, но не выполняет проверку молча. Решает всё равно ты.

## 6.4. Какие проверки имеет смысл вести

### Мониторинг нагрузки внешних API

**Зачем.** Чтобы поймать рост нагрузки до того, как уткнёшься в лимит сервиса или начнёшь платить за переход на следующий тариф.

**Периодичность:** еженедельно.

**Что делать:**
1. GET общее число задач/документов/событий по основным проектам в сервисе.
2. Прикинуть нагрузку: число объектов × частота заходов координатора × текущий интервал автопроверки.
3. Сравнить с прошлой неделей — растёт ли.
4. Если близко к лимиту тарифа — обсудить оптимизацию.

### Чистка канала коммуникации

**Зачем.** Каналы между ассистентами засоряются устаревшими записями. Через 3 месяца там может быть 100+ записей, из которых актуальны 5-10.

**Периодичность:** ежемесячно.

**Что делать:**
1. Открыть все файлы каналов.
2. Найти записи старше 30 дней.
3. Переместить в файл `archive/channels-YYYY-MM.md`.
4. В живом канале остаются только свежие.

### Сверка memory всех ассистентов

**Зачем.** У каждого ассистента — своя memory. Со временем общие правила (например, фидбек по работе пользователя) могут разойтись — один ассистент знает обновление, другой нет.

**Периодичность:** ежемесячно или по событию (после крупного фидбека).

**Что делать:**
1. Просмотреть memory каждого ассистента.
2. Найти расхождения в общих файлах (user_profile, feedback_*).
3. Привести к единому состоянию — самая свежая версия копируется во все memory.

### Сверка инструкций ассистентов

**Зачем.** CLAUDE.md и инструкции ролей могут устаревать (пути поменялись, правила обновились, ссылки на разделы поехали).

**Периодичность:** раз в 2-3 месяца.

**Что делать:**
1. Прочесть каждый CLAUDE.md.
2. Проверить ссылки на пути и разделы — все ли актуальны.
3. Проверить упоминания других ассистентов и каналов — нет ли устаревшего.
4. Поправить.

### Проверка GitHub-бэкапов

**Зачем.** Убедиться, что все локальные коммиты запушены, нет «оторвавшихся» репо.

**Периодичность:** еженедельно.

**Что делать:**
1. Для каждого репо ассистента — `git status` и `git log origin/main..main` (или похожее).
2. Если есть незапушенное — push.
3. Если есть конфликты — обсудить.

## 6.5. Календарные задачи

Помимо «по периодичности», бывают задачи **к конкретной дате**:
- Подача документов в Роспатент к такому-то числу.
- Проверка результата CI-сборки в понедельник.
- Напоминание о встрече.

Такие задачи лучше живут **в твоём планировщике** (Singularity, Todoist, и т.п.), а не в `recurring-tasks.md` инфраструктурщика. Через API координатор о них узнаёт — это и есть «соединение с реальной системой задач».

`recurring-tasks.md` — про **системные проверки оргструктуры**, не про твою работу.

---

## 6.6. Что НЕ ставить в регулярные проверки

- **«Раз в месяц проверять архитектуру бренда».** Это не системная задача, это содержательная работа — она в твоей зоне, не в зоне ассистента.
- **«Каждое утро докладывать статус всех проектов».** Это не проверка, это ритм работы. Если хочешь — пропиши в координаторе как поведение при первом сообщении.
- **«Раз в неделю проверять, не хочу ли я что-то менять в системе».** Это твоё решение, не «системная гигиена». Если что-то захочется — скажешь сама.

Принцип: регулярные проверки — **технические задачи мониторинга**, не содержательная работа.
