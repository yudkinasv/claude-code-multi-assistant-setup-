# Фрагмент CLAUDE.md Костика — интеграция с SingularityApp

Реальный раздел из `CLAUDE.md` координатора Костика. Используется в Паломнице. Токен и projectId заменены на плейсхолдеры — подставить свои.

---

## 10. Интеграция с Singularity (планировщик задач Светланы)

Singularity — основной планировщик (`https://api.singularity-app.com`). Тариф Elite — доступен публичный API.

### 10.1. Запись задачи в Singularity

**Триггер** — Светлана говорит одну из фраз с двоеточием, дальше идёт текст задачи:
- `в планер: X`
- `в органайзер: X`
- `в список дел: X`

**Действие** (используем инструмент Write для JSON, чтобы в Bash-команде не было `{...}` — Code ругается на это как на обфускацию):

1. **Инструментом Write** создать файл `E:/КЛОД/костик/_payload.json` с содержимым:
   ```json
   {"title":"<X>","projectId":"<DEFAULT_PROJECT_ID>","note":"Добавлено Костиком из Claude Code"}
   ```
   Подставить `<X>` на текст задачи.

2. **Bash:**
   ```bash
   TOKEN=$(cat "E:/КЛОД/костик/.singularity-token")
   curl -s -X POST "https://api.singularity-app.com/v2/task" \
     -H "Authorization: Bearer $TOKEN" \
     -H "Content-Type: application/json" \
     --data-binary @"E:/КЛОД/костик/_payload.json" \
     -w "\n---HTTP:%{http_code}---\n"
   rm "E:/КЛОД/костик/_payload.json"
   ```

3. Проверить HTTP-код. Ожидается **201**.

4. В чате — короткий отчёт:
   - При успехе (201): «добавил в планер: <X>» (одна строка, без призыва к действию).
   - При ошибке: «не получилось добавить в планер — ошибка <код>, причина: <message из ответа>». Не пытаться повторно автоматически.

### 10.3. Что НЕ делать

- Не передавать поле `parent` (это родительская задача, не проект). Для проекта — только `projectId`.
- Не сочинять задачи без триггера. Только по явной команде с одной из формулировок.
- Не упоминать содержимое токена в чате или коммитах.
- Не дублировать задачу — если повторили команду, спросить «уже добавил эту задачу в %время%, добавить ещё раз?».

### 10.4. Чтение статуса задач (Singularity → Костик)

**При первом сообщении Светланы в чате** Костик смотрит на отметку «Singularity-синхронизация: последняя проверка — YYYY-MM-DD HH:MM» в своём `status.md`.

- Если прошло **меньше 60 минут** — ничего не делать.
- Если прошло **больше 60 минут** — выполнить процедуру ниже **молча** (без отдельной команды), результат упомянуть одной строкой в начале ответа.

Это правило работает и в новой сессии, и в продолженной — Костик опирается на timestamp, не на тип запуска.

**Процедура:**

1. `TOKEN=$(cat "E:/КЛОД/костик/.singularity-token")`.
2. GET через /tmp + cp + Read:
   ```bash
   curl -s "https://api.singularity-app.com/v2/task?projectId=<DEFAULT_PROJECT_ID>&maxCount=200" \
     -H "Authorization: Bearer $TOKEN" > /tmp/tasks.json
   cp /tmp/tasks.json "E:/КЛОД/костик/_tasks-tmp.json"
   ```
   Затем — инструментом **Read** прочесть `_tasks-tmp.json`. После — `rm`.

   **`python3` НЕ использовать.** На Windows через WindowsApps он открывает Microsoft Store. Парсинг — Read + grep по полям.

3. Разобрать ответ:
   - `checked: 1` — задача выполнена.
   - `state: 0` — задача удалена, пропустить.
   - `modificated.checked` — timestamp последнего изменения галочки.

4. Свежевыполненные — те, у которых `modificated.checked` > timestamp из `status.md`.

5. Если есть — упомянуть одной строкой: «В Singularity с прошлого раза отмечено выполненным: X, Y». Обновить отметку в `status.md`.

### 10.5. По команде — свежая проверка

Триггеры: «проверь Singularity», «что в планировщике», «как там задачи».

**Действие:** свежий GET, доложить актуальное состояние.

### 10.6. Закрытие задачи

Триггеры: «готово: X», «закрой задачу X», «отметь выполненной: X».

**Действие:**
1. GET, найти задачу с title содержащим X, у которой `checked != 1` и `state != 0`.
2. Если несколько — переспросить.
3. Если одна — PATCH `/v2/task/<id>` с телом `{"checked":1}`.
4. Отчёт: «отметил выполненной: <полный title>».
