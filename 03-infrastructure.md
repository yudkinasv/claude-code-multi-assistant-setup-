# 3. Инфраструктура

Эта глава — про физическое размещение оргструктуры на диске и в git. Что куда положить, какие команды выполнить, какие настройки сделать.

---

## 3.1. Структура папок на диске

Заводим **корневую папку** под всю систему. У меня (в команде Паломницы) это `E:\КЛОД\`. У тебя может быть `~/code-team/`, `D:\Workspace\` — что угодно, главное — единый корень.

Внутри корня — папки ассистентов и проектов:

```
E:\КЛОД\
├── архип\                          ← инфраструктурщик (свой репо)
├── костик\                         ← координатор (свой репо)
├── Паломница\                      ← репо проекта 1 (main = главная сессия проекта)
├── паломница-brand-manager\        ← worktree специалиста (ветка brand-manager)
├── паломница-brand-strategist\     ← worktree специалиста (ветка brand-strategist) — когда заведём
├── (со временем)
│   ├── юбкина\                     ← репо проекта 2
│   └── трикотаж\                   ← репо проекта 3
└── code-orgstructure-template\     ← эта методичка
```

**Правила именования:**
- Имена ассистентов — кириллицей (костик, архип) или латиницей (kostik, arhip) — на твой вкус. Главное — единообразно.
- Worktree специалистов — `<проект>-<роль>` (например, `паломница-brand-manager`). Так сразу видно к какому проекту относится.
- Папки проектов — по названию проекта.

**Не создавать папки впрок.** Заводи только те, что прямо сейчас нужны. Если будут будущие — добавишь когда дойдёт.

---

## 3.2. Репо ассистента vs worktree ассистента

**Свой репозиторий** (как у Костика, Архипа) — когда:
- Ассистент работает **над несколькими проектами одновременно** (координатор, инфраструктурщик).
- Ассистент **не привязан к одному проекту физически** (его рабочие документы — не часть конкретного бренда).
- Хочешь чтобы у ассистента был **свой GitHub-бэкап** независимо.

**Worktree-ветка одного репо** (как у Глеба-менеджера в репо Паломницы) — когда:
- Ассистент работает **в одном проекте** (специалист, менеджер направления, писатель).
- Ему нужен **прямой доступ ко всем документам этого проекта** (концепция, архитектура, и т.п.).
- Финальные результаты его работы — **часть этого проекта** (брифы, тексты, артефакты бренда).

Выбор сделан — дальше команды.

## 3.3. Создание собственного репо ассистента

Допустим, заводим координатора по имени Костик.

```bash
# Создать папку и инициализировать git
mkdir -p E:/КЛОД/костик
cd E:/КЛОД/костик
git init
git branch -m master main
git config user.name "Ваше Имя"
git config user.email "you@example.com"
```

Создать приватный репо на GitHub (через веб-интерфейс):
1. Зайти на https://github.com/new
2. Repository name: `kostik-assistant` (или другое)
3. Visibility: **Private** (важно — у ассистента в файлах может быть рабочая информация)
4. **Не** ставить галочки «Add README», «.gitignore», «license»
5. Create repository
6. Скопировать URL вида `https://github.com/<username>/kostik-assistant.git`

Привязать origin и сделать первый коммит:

```bash
git remote add origin https://github.com/<username>/kostik-assistant.git
# (создать CLAUDE.md, .gitignore, README.md — см. главу 8 чек-лист)
git add .
git commit -m "init: каркас репо координатора"
git push -u origin main
```

После первого push — у ассистента есть offsite-бэкап. Дальше **правило: после каждого значимого коммита делать `git push`**.

## 3.4. Создание worktree-ветки специалиста

Допустим, у нас есть репо проекта Паломница (`E:\КЛОД\Паломница\`), и мы хотим завести специалиста Глеба в отдельной ветке.

```bash
# Из любой папки этого репо
git -C E:/КЛОД/Паломница worktree add -b brand-manager E:/КЛОД/паломница-brand-manager main
```

Что делает эта команда:
- Создаёт новую ветку `brand-manager` от `main`.
- Делает checkout этой ветки в папку `E:\КЛОД\паломница-brand-manager\` (отдельный файловый рабочий каталог).
- В этой папке Глеб видит **весь репо Паломницы**, но любые его правки идут **в ветку brand-manager**, не в main.

Удалить worktree (когда роль закрыта):
```bash
git -C E:/КЛОД/Паломница worktree remove E:/КЛОД/паломница-brand-manager
```

Если worktree «занят» процессом Claude Code — удаление физической папки может не пройти (Windows блокирует). Закрой сессию ассистента, потом повтори. Запись о worktree из git-реестра снимется в любом случае.

## 3.5. Профили Windows Terminal (Windows)

Делаем чтобы один клик в выпадашке `+` открывал нужного ассистента в нужной папке.

Открыть settings.json:
1. В Windows Terminal — стрелка ▼ рядом с `+`.
2. «Параметры» → внизу «Open JSON file» (или соответствующая надпись).

Добавить в массив `"profiles" → "list"` блоки для каждого ассистента:

```json
{
    "guid": "{11111111-aaaa-bbbb-cccc-111111111111}",
    "name": "Костик-ассистент",
    "tabTitle": "Костик-ассистент",
    "suppressApplicationTitle": true,
    "commandline": "%SystemRoot%\\System32\\WindowsPowerShell\\v1.0\\powershell.exe -NoExit -Command \"claude -c\"",
    "startingDirectory": "E:\\КЛОД\\костик",
    "hidden": false,
    "tabColor": "#CC3333"
}
```

**Что важно:**
- **guid** — должен быть **уникальным** (валидный hex-формат 8-4-4-4-12). Можно использовать паттерны вида `{22222222-aaaa-bbbb-cccc-222222222222}` для второго профиля.
- **suppressApplicationTitle: true** — иначе Claude Code будет перезаписывать имя вкладки на «Claude Code» или путь к папке.
- **tabTitle** — явно задаёт имя на вкладке. Должно совпадать с `name`.
- **commandline** — `claude -c` вместо `claude` означает «продолжить последнюю сессию». Полезно для continuity. Подробнее — см. главу 7 (грабли).
- **startingDirectory** — путь к рабочей папке ассистента. **Двойные слэши `\\`** — потому что это JSON.
- **tabColor** — цветной маркер вкладки. Помогает не путать ассистентов визуально.

Между блоками — запятая. После последнего блока — запятой нет.

**На Mac/Linux** — аналог через профили iTerm2 (Mac) или скрипты bash + alias (Linux). Главная идея та же: одна команда / один клик = открытие в нужной папке с автозапуском.

## 3.6. Memory и projectId

Claude Code хранит память каждого «проекта» (= рабочей папки) в служебной директории:
- Windows: `C:\Users\<user>\.claude\projects\<projectId>\`
- Mac/Linux: `~/.claude/projects/<projectId>/`

`<projectId>` генерируется автоматически из пути рабочей папки. Правило (упрощённо для Code):
- Латинские буквы и цифры — сохраняются.
- Дефисы (`-`) — сохраняются.
- Всё остальное (двоеточия, слэши, кириллица, и т.п.) — заменяется на дефис.

Пример:
- Папка `E:\КЛОД\костик\` → projectId `E-------------` (E + 13 дефисов от `:`, `\`, `КЛОД`, `\`, `костик`).
- Папка `E:\КЛОД\паломница-architect\` → projectId `E-----------------architect`.

Внутри папки projectId — файл `MEMORY.md` (индекс) и отдельные `*.md` файлы (профиль, feedback-и, проектные заметки). См. главу 8 (чек-лист) для шаблонов.

**Если ассистент должен «знать что-то с порога» при первом запуске** — положить нужные `*.md` файлы в его memory **до того**, как ты впервые запустишь Claude Code в его папке. Code подхватит memory при первом старте.

**Миграция memory** между папками (например, при переезде ассистента) — обычным `cp` файлов из старой projectId-папки в новую.

## 3.7. Allow-list (.claude/settings.local.json)

Чтобы Claude Code не спрашивал подтверждение на каждую безопасную операцию (`Read`, `Write`, простые git-команды), кладём список разрешений в файл:

`<рабочая-папка-ассистента>/.claude/settings.local.json`

Базовый шаблон:

```json
{
  "permissions": {
    "allow": [
      "Read",
      "Glob",
      "Grep",
      "Edit",
      "Write",
      "Agent",
      "WebFetch",
      "WebSearch",
      "Bash(cat:*)",
      "Bash(curl:*)",
      "Bash(grep:*)",
      "Bash(rm:*)",
      "Bash(cp:*)",
      "Bash(ls:*)",
      "Bash(wc:*)",
      "Bash(git status:*)",
      "Bash(git diff:*)",
      "Bash(git log:*)",
      "Bash(git add:*)",
      "Bash(git commit:*)",
      "Bash(git push)",
      "Bash(git fetch:*)",
      "Bash(git pull:*)"
    ]
  }
}
```

**Что включено:**
- Чтение/правка/поиск файлов без подтверждений.
- Сетевые операции (WebFetch, WebSearch, curl).
- Базовые bash-утилиты (cat, grep, rm, cp, ls, wc).
- Безопасные git-команды (status, log, add, commit, push без force).

**Что НЕ включено намеренно** (требует подтверждения):
- `git push --force` — может затереть чужую работу.
- `git reset --hard` — теряет локальные изменения.
- `git checkout --` — теряет несохранённое.

**Шаблон шире** (`Bash(git *)` вместо точечного списка) — удобнее, но включает опасные команды. Для координатора и инфраструктурщика я бы оставил точечный, для специалистов в worktree можно широкий.

**`.gitignore`** должен исключать `settings.local.json` — это локальные разрешения, не уходят в репо.

## 3.8. .gitignore

Минимальный `.gitignore` для каждого ассистента:

```gitignore
# Windows / OS
Thumbs.db
desktop.ini
Desktop.ini
.DS_Store

# Office temp files
~$*.docx
~$*.xlsx
~$*.pptx

# IDE
.vscode/
.idea/

# Claude Code локальные настройки
.claude/settings.local.json

# Секреты (токены API внешних сервисов)
*.token
*.secret
.singularity-token
.notion-token
.todoist-token

# Временные файлы парсинга
_*.json
_tmp*
```

**Принцип:** в git попадает то, что нужно для воспроизведения — инструкции, документы. **Не попадает:** локальные настройки одного компьютера, токены, временные файлы.

## 3.9. Стартовый промпт ассистента

При первом запуске нового ассистента (`claude` в его папке) — Code открывает чистую сессию. У него ещё нет контекста о том, кто он.

Решение: **стартовый промпт**. Текст, который ты копируешь в первое сообщение. В нём:
- Кратко сказано «ты — такой-то, твоя роль такая-то».
- Перечислены файлы, которые он должен прочитать (CLAUDE.md, профиль из memory, инструкция роли).
- Сказано что делать после прочтения («жду первого вопроса», или конкретное первое задание).

Стартовый промпт хранится в репо ассистента (например, в `docs/handover-launch.md`), чтобы при следующем запуске не воссоздавать его с нуля.

Шаблон стартового промпта — в `templates/launch-prompt.template.md`.
