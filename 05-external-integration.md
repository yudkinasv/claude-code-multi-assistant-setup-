# 5. Внешние интеграции

Подключение Claude Code к внешним сервисам через REST API. На примере **SingularityApp** (онлайн-планировщик задач) — рецепт применим к любому сервису, имеющему API с Bearer-токеном (Notion, Todoist, Trello, и т.д.).

---

## 5.1. Зачем это нужно

Внутри Claude Code твоя «вселенная» — файлы на диске. Внешний мир — за её пределами:
- Планировщик задач, в котором ты живёшь ежедневно (Singularity, Todoist, TickTick).
- Notion/Obsidian/Roam с твоей базой знаний.
- Календарь.
- Trello/Jira/Linear с командными досками.
- CRM с клиентами.
- Email-инбокс.

Интеграция через API делает их **видимыми ассистенту**. Он:
- **Пишет** туда задачи, события, заметки.
- **Читает** оттуда статусы, обновления.
- **Меняет** (отмечает выполненным, обновляет, удаляет).

Это превращает координатор-ассистента из «помощника в чате» в **активный мост** между внутренней работой Claude Code и твоей реальной системой задач.

---

## 5.2. Требования к сервису

Для интеграции нужны:

1. **Публичный REST API**. Большинство современных сервисов его имеют (на платных тарифах часто).
2. **Аутентификация по токену** (Bearer token / API key). Простой механизм без OAuth-flow.
3. **Документация** или Swagger/OpenAPI-spec — чтобы найти endpoints и формат запросов.
4. **Свой тариф/подписка**, если API закрыт для бесплатных пользователей. Например, у SingularityApp — на тарифе Elite.

Если сервис не подходит — интеграция невозможна. Это первая проверка.

---

## 5.3. Получение токена

В большинстве сервисов токен создаётся в личном кабинете. У SingularityApp:
1. В личном кабинете — раздел «API доступ» (или «API access»).
2. Кнопка «Создать токен».
3. Имя токена — например, `kostik-bot` (чтобы потом помнить, для чего создан).
4. Выбрать **scope** — какие операции токен может (создание задач, чтение проектов, и т.п.).
5. Скопировать токен сразу — после закрытия страницы его обычно не показывают повторно.

**Безопасность:**
- **Не пересылай токен в публичных каналах** (открытый чат, GitHub-репо).
- Если случайно отправила в чат Claude Code — токен сохранился в локальный jsonl-файл сессии. Это не утечка в интернет, но если вдруг будешь делиться этим компом — после интеграции лучше **пересоздать токен** (старый удалить в ЛК, создать новый).
- **Никогда не комитить токен в git.** Даже в приватный репо.

---

## 5.4. Куда положить токен

Создаём файл в репо координатора:

`E:\КЛОД\<координатор>\.<сервис>-token`

Например: `E:\КЛОД\костик\.singularity-token`. В файле — одна строка, сам токен.

В `.gitignore` репо обязательно:
```gitignore
.singularity-token
.notion-token
.todoist-token
*.token
*.secret
```

Это исключает токены из коммитов. Файл живёт только локально, в репо не попадает.

---

## 5.5. Поиск базового URL и схемы запросов

Чтобы делать запросы, нужно знать:
- **Base URL** (например, `https://api.singularity-app.com/v2`).
- **Заголовок аутентификации** (обычно `Authorization: Bearer <token>`).
- **Endpoints** для нужных операций (GET список, POST создать, PATCH обновить, DELETE удалить).
- **Формат тела запроса** (какие поля передавать).

**Где это искать:**
1. **Документация сервиса** на их сайте. Иногда там полное описание API.
2. **Swagger/OpenAPI** — большинство сервисов на NestJS/Django REST/FastAPI публикуют интерактивную документацию по пути типа `/api`, `/api-docs`, `/swagger`. Swagger-страница в браузере чаще всего рендерится JavaScript-ом — Claude Code через WebFetch видит её пустой. Решение: запросить **JSON-спецификацию** напрямую (`/api-json`, `/v2/api-json`, или похожее). Это plain JSON, его можно скачать и распарсить.

Пример для Singularity:
```bash
curl https://api.singularity-app.com/v2/api-json -o /tmp/swagger.json
```

Внутри `/tmp/swagger.json` — описание всех endpoints, всех DTO (входных схем), всех типов ответов. Можно искать через `grep` (см. главу 7 «грабли» про парсинг JSON без python).

## 5.6. Первый тест — GET (чтение)

Самая безопасная операция — `GET` (читает, ничего не меняет). С неё начинаем.

```bash
TOKEN=$(cat "E:/КЛОД/<координатор>/.<сервис>-token")
curl -s "https://api.singularity-app.com/v2/project" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Accept: application/json" \
  -w "\nHTTP: %{http_code}\n"
```

**Что ожидаешь:**
- HTTP 200 — токен валиден, запрос принят.
- HTTP 401 — токен невалиден или не имеет scope для этого endpoint.
- HTTP 404 — endpoint неправильный.
- HTTP 5xx — проблема на стороне сервиса (редко).

Если 200 — посмотри тело ответа, найди структуру (что-то вроде `{"projects": [...]}`). Это вход в данные.

---

## 5.7. Тест POST (создание)

После того как `GET` сработал — пробуем создать что-то. **Важно:** это создаст реальный объект в твоём аккаунте сервиса. Можешь договориться с собой о **тестовых» названиях** («тест от Х, можно удалить»).

Пример создания задачи в SingularityApp:

```bash
TOKEN=$(cat "E:/КЛОД/<координатор>/.<сервис>-token")
cat > /tmp/payload.json <<'EOF'
{
  "title": "Тест от Х, можно удалить",
  "projectId": "P-...",
  "note": "Тестовый запрос API"
}
EOF
curl -s -X POST "https://api.singularity-app.com/v2/task" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  --data-binary @/tmp/payload.json \
  -w "\nHTTP: %{http_code}\n"
```

**Что ожидаешь:**
- HTTP 201 — задача создана. В теле ответа — её ID и все поля. Зайди в сервис в браузере, проверь что задача появилась.
- HTTP 400 — ошибка в формате запроса. Внимательно прочитай message в ответе — часто указано, какое поле неверное.
- HTTP 401 — проблема с токеном.

**Грабли с brace-обфускацией.** Если используешь Bash heredoc с JSON-телом (как выше) — Claude Code будет видеть в команде `{...}` с кавычками и просить подтверждения как для обфускированной команды, **даже если у тебя есть `Bash(curl:*)` в allow-list**. Обход — генерировать payload через инструмент Write (не через heredoc):

В правилах ассистента прописать:
1. **Write tool** создаёт файл `E:/КЛОД/<координатор>/_payload.json` с JSON-содержимым.
2. **Bash** делает `curl ... --data-binary @"E:/КЛОД/<координатор>/_payload.json"` — здесь brace нет, Code не ругается.
3. **Bash** `rm` удаляет временный файл.

Это даёт чистый рабочий цикл без подтверждений на каждый запрос.

---

## 5.8. Тест PATCH (обновление) и DELETE

После того как POST работает — пробуем обновить созданную задачу (например, отметить выполненной).

```bash
TOKEN=$(cat "E:/КЛОД/<координатор>/.<сервис>-token")
curl -s -X PATCH "https://api.singularity-app.com/v2/task/<task-id>" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"checked":1}' \
  -w "\nHTTP: %{http_code}\n"
```

И удаление (для тестовых задач):

```bash
curl -s -X DELETE "https://api.singularity-app.com/v2/task/<task-id>" \
  -H "Authorization: Bearer $TOKEN" \
  -w "HTTP: %{http_code}\n"
```

После теста — **удали все тестовые задачи** в сервисе, чтобы не засорять.

## 5.9. Прописывание API в правила координатора

Когда тесты прошли — оформляем в CLAUDE.md координатора. Раздел вида:

```markdown
## Интеграция с <сервис>

### Запись задачи

**Триггер** — пользователь говорит:
- «в планер: X»
- «в органайзер: X»
- «в список дел: X»

**Действие:**
1. Создать payload через Write tool в файл `E:/КЛОД/<координатор>/_payload.json`:
   ```json
   {"title":"<X>","projectId":"<default-project-id>"}
   ```
2. Bash: POST на API + удалить файл после.
3. Отчитаться: «добавил в планер: <X>».

### Чтение задач

**При первом сообщении пользователя в чате** (если с последней проверки прошло больше 60 минут):
1. GET список задач проекта по умолчанию.
2. Сохранить ответ через `curl ... > /tmp/tasks.json; cp /tmp/tasks.json E:/КЛОД/<координатор>/_tasks-tmp.json`.
3. Прочесть через Read + grep по нужным полям (HE использовать python3 — см. главу 7).
4. Если есть свежевыполненные задачи (по timestamp поля `checked`) — упомянуть пользователю.
5. Удалить временный файл.

### Закрытие задачи

**Триггер** — пользователь говорит:
- «готово: X»
- «закрой задачу X»

**Действие:**
1. GET задачи (как выше).
2. Найти задачу с title содержащим X.
3. Если совпадение однозначное — PATCH с `{"checked":1}`.
4. Если совпадений больше одного — переспросить пользователю, какую именно.
5. Отчитаться: «отметил выполненной: <title>».
```

Полный пример таких правил — в `examples/kostik-coordinator-singularity.md`.

## 5.10. Что подключать через API, а что нет

**Подключать:**
- Сервисы, в которых ты живёшь ежедневно (планировщик задач, календарь).
- Сервисы с **актуальным состоянием**, которое влияет на работу (CRM с активными сделками, доска проекта).
- Сервисы с **большим объёмом данных**, которые непрактично копировать вручную (база знаний на тысячи документов).

**Не подключать:**
- Сервисы, которые ты используешь раз в месяц — оверхед на настройку не окупится.
- Сервисы без публичного API.
- Сервисы, где доступ через API существенно дороже подписки (некоторые AI-агрегаторы).
- Сервисы, для которых уже есть нативная интеграция в Code (если в будущем такие появятся).

---

## 5.11. Лимиты и нагрузка

У каждого сервиса есть **лимиты** на количество запросов в минуту/час/день. У большинства они достаточно большие для индивидуального использования (тысячи запросов в день), но при автопроверке каждый час из нескольких ассистентов можно их перебрать.

**Соображения:**
- Считай примерно сколько запросов в день делает ассистент.
- Сравни с лимитом сервиса (обычно указан в документации API).
- Если близко — увеличь интервал автопроверки (например, с 60 минут до 2 часов).

**Дополнительно — мониторинг нагрузки.** Заведи у инфраструктурщика регулярную проверку (см. главу 6 «регулярные проверки»):
- Раз в неделю — посчитать, сколько API-запросов сделал координатор за неделю.
- Сравнить с пределами твоего тарифа.
- Если приближаешься — оптимизировать (увеличить интервал, фильтровать запросы по дате модификации).
