# 4. Каналы коммуникации

Здесь — как ассистенты «разговаривают» друг с другом, не имея прямого доступа к чужим сессиям.

---

## 4.1. Базовый принцип

Каждая сессия Claude Code — это отдельная память. Один чат не знает, что обсуждается в другом. Прямого «межпроцессного» общения нет.

Поэтому общение идёт через **файлы**:
- Ассистент A хочет передать сообщение ассистенту B.
- A пишет в файл (например, `for-B.md`).
- При следующем заходе B читает этот файл, видит сообщение, реагирует.

Это медленнее живого общения, но даёт три плюса:
- **Устойчиво** — файл лежит на диске, не теряется.
- **Прозрачно** — ты в любой момент видишь, кто что кому передал.
- **Воспроизводимо** — переустановила Code, восстановила репо из git — переписка между ассистентами сохранена.

---

## 4.2. Модель парных каналов

Самый простой вариант — **парные каналы**. Для каждой пары ассистентов A и B заводится два файла:

- `for-B.md` (в репо B, или в worktree A — варианты ниже) — A пишет, B читает.
- `for-A.md` (в репо A) — B пишет, A читает.

Это даёт **двусторонний канал** A ↔ B.

**Где физически живёт файл:**

Вариант 1. **Файл в репо получателя.**
- `for-B.md` лежит в репо B.
- A пишет туда через `git -C <путь-к-репо-B>` — то есть «через границу репо», работает в свою чужую папку.
- Плюс: B видит файл «у себя дома», читает по простому пути.
- Минус: A нужны разрешения в allow-list на запись/коммит в чужой репо.

Вариант 2. **Файл в репо/worktree отправителя.**
- `for-B.md` лежит в репо/worktree A.
- B читает оттуда по абсолютному пути (`E:\<путь-к-A>\for-B.md`).
- Плюс: каждый ассистент пишет только в своё пространство — нет проблем с границами репо.
- Минус: B должен знать конкретный путь, и при изменении конфигурации (переезд A) ссылка ломается.

**В реальной системе Паломницы используется смешанная модель:**
- От Корнея (main репо Паломницы) к Костику (свой репо): файл `docs/for-kostik.md` в репо Паломницы (вариант 2).
- От Костика к Корнею: файл `for-korney.md` в репо Костика (вариант 2).
- От Глеба (worktree brand-manager) к Костику: файл `brand-team/for-kostik.md` в ветке brand-manager (вариант 2). Костик читает по полному пути worktree.
- От Костика к Глебу: файл `for-glebb.md` в репо Костика (вариант 2).

Принцип: **каждый ассистент пишет только в своё пространство**, читатели приходят по абсолютным путям.

## 4.3. Триггеры записи

Чтобы ассистент знал, **когда** ему писать в канал, в его CLAUDE.md прописываются триггеры — конкретные фразы пользователя.

Пример (правило в CLAUDE.md ассистента A):

> **Триггер записи в канал к B** — пользователь говорит одну из фраз:
> - «передай B X»
> - «запиши для B X»
> - «пусть B знает X»
>
> **Действие:**
> 1. Дописать в файл `<путь>/for-B.md` запись в формате:
>    ```
>    ## YYYY-MM-DD HH:MM (от <моё имя>)
>    <текст>
>    ```
>    В конец файла.
> 2. Коммит: `channel: для B — <краткая суть>`.
> 3. Push.
> 4. В чате пользователю — короткий отчёт: «передал B».

**Почему именно фразы с двоеточием.** Они однозначны для парсинга. «Передай B что задача отменена» — Code может понять как просто разговор. «Передай B: задача отменена» — чёткий триггер, ассистент сразу понимает: всё после двоеточия идёт в файл.

**Используй формулировки естественной речи**, но фиксированный набор. У меня в системе Паломницы: «передай X», «запиши для X», «пусть X знает X», «отметь X». Достаточно 3-4 синонимов на язык.

---

## 4.4. Формат записи

```markdown
## YYYY-MM-DD HH:MM (от <имя отправителя>)

<текст одной мыслью>
```

**Почему так:**
- **Дата+время** в заголовке — для timestamp-сравнения при автопроверке (см. ниже).
- **Имя отправителя** в скобках — критично если в канал пишут несколько ассистентов (например, общий inbox).
- **Markdown заголовок ##** — легко находится через grep.
- **Один пункт = одна мысль.** Если есть несколько вещей передать — несколько записей с разными timestamp.

Новые записи — **в конец файла** (свежие внизу). Это упрощает append. Если хочется свежие сверху — пиши **выше последней записи**, но в наших правилах принят append.

---

## 4.5. Автопроверка канала при первом сообщении сессии

Канал бесполезен, если получатель не помнит проверять. Решение — **прописать в его правилах автопроверку**.

**Правило в CLAUDE.md получателя:**

> **При первом сообщении пользователя в чате** (новом или продолженном через `claude -c`) — проверить файл-канал.
>
> 1. Прочесть отметку «Канал X: последняя проверка — YYYY-MM-DD HH:MM» в своём `status.md`.
> 2. Если с этой отметки прошло **меньше 60 минут** — ничего не делать, отвечать как обычно.
> 3. Если прошло **больше 60 минут** или отметки нет:
>    - Прочесть файл-канал целиком.
>    - Найти записи с timestamp свежее последней отметки.
>    - Если есть — упомянуть пользователю одной строкой в начале ответа: «у X для меня свежая запись от HH:MM — <короткая суть>, учёл».
>    - Если нет — ничего не упоминать (молчаливая проверка).
>    - Обновить отметку в `status.md` на текущий момент.

**Почему по таймеру, не «при старте сессии».** Если в профиле терминала прописано `claude -c` (continue last) — каждый новый запуск Code **продолжает** старую сессию, не «стартует» новую. Правило «при старте» не сработает. Таймер работает в любом случае.

**Интервал 60 минут** — компромисс между свежестью и нагрузкой. Меньше — больше API/диск-операций; больше — поздно узнаёшь свежее. Подбери под себя.

---

## 4.6. Триггер чтения по команде

В дополнение к автопроверке, ассистент должен делать **свежее чтение по явной команде**.

**Правило в CLAUDE.md получателя:**

> **Триггер свежей проверки** — пользователь говорит:
> - «проверь канал»
> - «что от X»
> - «как там сообщения»
>
> **Действие:** прочесть файл-канал целиком (даже если по таймеру не пора), доложить состояние: сколько записей с последней проверки, что в них.

Это пригодится, когда:
- Ты только что в другом чате что-то отправила и хочешь чтобы получатель увидел сразу.
- Прошло меньше 60 минут с предыдущей проверки, но ты знаешь что должно быть что-то новое.

## 4.7. Один или много каналов на ассистента

С ростом команды у одного получателя может скопиться много отдельных файлов-каналов:
- `for-X.md` (от Y)
- `for-X-from-Z.md` (от Z)
- `for-X-from-W.md` (от W)
- ...

**Парная модель** с отдельным файлом на пару — простая, но плохо масштабируется на 5+ ассистентов.

**Альтернативы:**

**Модель «общий inbox».** У получателя X — один файл `inbox.md`, в который **все** пишут. Запись начинается с пометки «от Y/Z/W». Плюс — один файл, мало шума. Минус — потенциальные конфликты при одновременной записи (если такое произойдёт; на практике с ИИ-ассистентами редко).

**Модель «папка каналов».** У получателя X — папка `channels/from-Y.md`, `channels/from-Z.md`, и т.д. По одному файлу на отправителя, но сгруппировано. X при автопроверке проходит по папке.

В реальной системе Паломницы пока используется **парная модель** — команда из 4 ассистентов это позволяет. Когда вырастет до 6-8 — стоит переходить на общий inbox.

## 4.8. Отчёт об отправке в чат

После записи в канал ассистент должен **коротко отчитаться** пользователю: «передал X». Одна строка. Без призыва к действию вроде «теперь зайди в X и скажи прочти канал».

Почему так:
- Если автопроверка по таймеру настроена — никакого действия от пользователя не нужно.
- Если пользователь хочет ускорить — он сам зайдёт в получателя и скажет «проверь канал».
- Дополнительные подсказки в чате — шум, который усложняет работу пользователя со временем.

Минимализм отчётов — часть гигиены системы.

---

## 4.9. Что в канал писать, что не писать

**Писать в канал:**
- Решения долгосрочного действия («архитектура слогана отложена», «пилот по новой схеме»).
- Перестановки в очереди задач («после X идёт Y, не Z как думали»).
- Изменения по ролям («Z закрыл задачу», «W вошёл в работу»).
- Договорённости, которые нужно учитывать на расстоянии (не в этой сессии, а через дни).

**НЕ писать в канал:**
- Рутинные оперативные обновления (это шум, заваливает читателя).
- Содержимое финальных артефактов (тексты, файлы) — они в собственных местах.
- Изменения архитектуры и якорей — это решение пользователя, идёт через основную ветку, не через канал.
- Эмоции и социальные жесты.

**Правило «канал = переписка между руководителями отделов», не «переписка между сотрудниками».** Содержательное, редкое, по делу.
