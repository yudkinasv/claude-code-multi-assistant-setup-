# 8. Чек-лист запуска

Пошаговый recipe «развернуть многоассистентную оргструктуру с нуля». Ориентировочно 4-8 часов на полную сборку (один человек, без помощников).

Перед запуском — прочти главы 1-2 (концепция и роли). При исполнении — открывай главы 3-7 (инфраструктура, каналы, интеграции, регулярные проверки, грабли) для деталей.

---

## Этап 1. Планирование (30-60 минут)

### 1.1. Определи свои проекты

- [ ] Сколько у тебя проектов (брендов / направлений / клиентов)? Назови их.
- [ ] Сколько активных сейчас и сколько на горизонте?
- [ ] Главный приоритет периода — для какого проекта?

### 1.2. Определи роли в команде

Минимальный комплект:
- [ ] **Координатор** — один, над всеми проектами.
- [ ] **Главная сессия проекта-приоритета** — для оперативной работы.

Дополнительно (если есть нагрузка):
- [ ] **Инфраструктурщик** — если планируешь часто перенастраивать систему, заводить новые роли.
- [ ] **Специалисты по направлениям** — для конкретных функций (бренд-менеджмент, юридика, и т.п.).
- [ ] **Писатели/стратеги** — для творческих жанров.

Запиши их в табличку: имя — роль — где живёт (свой репо / worktree-ветка какого проекта).

### 1.3. Определи интеграции

- [ ] Какой у тебя основной планировщик задач (Singularity, Todoist, Notion)?
- [ ] У него есть публичный API (Bearer token)?
- [ ] Твой тариф открывает доступ к API?

Если нет — пропусти этап 5 (интеграции), используй систему без внешних API.

---

## Этап 2. Корневая папка и инфраструктура (15 минут)

### 2.1. Создай корневую папку

- [ ] Создай папку для всей системы. У меня — `E:\КЛОД\`, у тебя может быть `~/code-team/`, `D:\Workspace\`.

### 2.2. Подготовь GitHub-аккаунт

- [ ] Залогинься на github.com.
- [ ] Включи 2FA, если ещё не включено.
- [ ] Сохрани recovery-коды на бумаге (см. главу 7.11).

---

## Этап 3. Сборка ассистентов «своего репо» (45 минут на каждого)

Для каждого ассистента с собственным репо (координатор, инфраструктурщик):

### 3.1. Локальный репо

- [ ] `mkdir -p <корневая>/<имя-ассистента>` (например, `E:/КЛОД/координатор/`).
- [ ] `cd <корневая>/<имя-ассистента>`.
- [ ] `git init`.
- [ ] `git branch -m master main`.
- [ ] `git config user.name "<твоё имя>"`.
- [ ] `git config user.email "<твой email>"`.

### 3.2. GitHub-репо

- [ ] Создай **приватный** репо на github.com/new (имя — например, `coord-assistant`).
- [ ] Не ставь галочки «README», «.gitignore», «license».
- [ ] Скопируй URL вида `https://github.com/<username>/coord-assistant.git`.

### 3.3. Привязка origin

- [ ] `git remote add origin <URL>`.

### 3.4. Стартовые файлы

Из папки `templates/` этой методички возьми и адаптируй:
- [ ] `CLAUDE.md` (правила репо ассистента, его роль, что делает / не делает).
- [ ] `.gitignore` (стандарт + токены + временные файлы).
- [ ] `docs/handover-launch.md` (стартовый промпт для первой сессии).

### 3.5. Первый коммит и push

- [ ] `git add .`
- [ ] `git commit -m "init: каркас репо <имя ассистента>"`.
- [ ] `git push -u origin main`.

### 3.6. Memory

- [ ] Создай папку `C:\Users\<user>\.claude\projects\<projectId>\memory\` (projectId предсказывается по пути ассистента — см. главу 7.8).
- [ ] Положи туда из `templates/memory/`:
  - `MEMORY.md` (индекс).
  - `profile_<имя>.md` (профиль роли).
  - Общие feedback-файлы по работе с тобой.

### 3.7. Профиль терминала

- [ ] В Windows Terminal → стрелка ▼ рядом с `+` → «Параметры» → «Open JSON file».
- [ ] Добавь профиль ассистента (шаблон в `templates/terminal-profile.template.json`):
  - Уникальный `guid`.
  - `name`, `tabTitle`, `suppressApplicationTitle: true`.
  - `startingDirectory` — путь к папке ассистента.
  - `commandline` — `claude` (не `-c` для первого запуска, потом поменяешь).
  - `tabColor` — на твой выбор.

### 3.8. Первый запуск

- [ ] Открой новую вкладку через профиль.
- [ ] В первое сообщение скопируй стартовый промпт из `docs/handover-launch.md` целиком.
- [ ] Ассистент прочитает CLAUDE.md, memory, представится.
- [ ] Скажи `/exit`, закрой вкладку.

### 3.9. Переключение на `claude -c`

- [ ] В `settings.json` Terminal — меняй `"commandline"` ассистента с `claude` на `claude -c`. Теперь при каждом следующем запуске будет продолжаться последняя сессия.

---

## Этап 4. Сборка ассистентов worktree-веток (30 минут на каждого)

Для каждого специалиста, привязанного к одному проекту:

### 4.1. Создай ветку и worktree

- [ ] Из любой папки **главного репо проекта**:
  ```bash
  git -C <путь-к-репо-проекта> worktree add -b <имя-роли> <путь-к-новой-папке> main
  ```
  Например: `git -C E:/КЛОД/Паломница worktree add -b brand-manager E:/КЛОД/паломница-brand-manager main`.

### 4.2. Инструкция роли

- [ ] В новой папке worktree создай подпапку (например, `brand-team/` или `roles/`).
- [ ] Внутри — файл `<имя-роли>.md` с полной инструкцией (шаблон в `templates/role-instruction.template.md`).
- [ ] Опционально — папка `previous-work/` для наследия из прошлых сессий (если переезжаешь с claude.ai в Code).

### 4.3. Коммит в ветку

- [ ] `git -C <путь-к-worktree> add .`
- [ ] `git -C <путь-к-worktree> commit -m "init: запуск <роли>"`.
- [ ] `git -C <путь-к-worktree> push -u origin <имя-ветки>`.

### 4.4. Memory под projectId worktree

- [ ] Аналогично 3.6 — создай папку memory под projectId worktree-папки.

### 4.5. Профиль терминала и первый запуск

- [ ] Аналогично 3.7-3.8.

---

## Этап 5. Каналы коммуникации (60 минут)

Для каждой пары ассистентов, которые должны общаться:

### 5.1. Создай файлы каналов

- [ ] В репо/worktree отправителя — файл `for-<получатель>.md` (шаблон в `templates/channel-file.template.md`).
- [ ] В репо/worktree получателя — файл `for-<отправитель>.md`.

### 5.2. Пропиши правила в CLAUDE.md

Для каждого ассистента в его CLAUDE.md добавь раздел «Каналы коммуникации» (шаблон в `templates/channel-rules.template.md`):

- [ ] Триггеры записи в канал (фразы пользователя).
- [ ] Процедура записи (формат, коммит, push, отчёт).
- [ ] Правило автопроверки при первом сообщении (таймер 60 минут).
- [ ] Правило свежей проверки по команде.

### 5.3. Тест

- [ ] Скажи отправителю «передай <получателю>: тест канала».
- [ ] Открой вкладку получателя, напиши любое сообщение.
- [ ] Проверь, что в начале ответа получателя появилось «у <отправителя> для меня свежая запись от HH:MM — ...».

---

## Этап 6. Внешний API (90 минут — опционально)

Если есть планировщик с API:

### 6.1. Токен

- [ ] В ЛК сервиса создай API-токен.
- [ ] Положи токен в файл `<координатор>/.<сервис>-token`.
- [ ] Проверь, что `.<сервис>-token` в `.gitignore`.

### 6.2. Документация

- [ ] Найди base URL API сервиса.
- [ ] Найди Swagger JSON-spec (`/api-json` или похожее).
- [ ] Изучи endpoints и DTO для нужных операций (GET список, POST создать, PATCH обновить).

### 6.3. Тесты

- [ ] GET — прочитай список объектов. Должен вернуть HTTP 200.
- [ ] POST — создай тестовый объект «Тест от Х, можно удалить». HTTP 201.
- [ ] PATCH — отметь его выполненным. HTTP 200/204.
- [ ] DELETE — удали тестовый. HTTP 204.

### 6.4. Правила в CLAUDE.md координатора

- [ ] Добавь раздел «Интеграция с <сервис>» (шаблон в `templates/api-integration-rules.template.md`):
  - Триггеры записи задачи.
  - Процедура (Write payload → curl → удалить).
  - Триггеры чтения, закрытия.
  - Автосинхронизация по таймеру.

### 6.5. Allow-list

- [ ] В `<координатор>/.claude/settings.local.json` добавь:
  - `Bash(curl:*)`, `Bash(cat:*)`, `Bash(rm:*)`, `Bash(cp:*)`, `Bash(grep:*)`, `Bash(ls:*)`, `Bash(wc:*)`.

---

## Этап 7. Регулярные проверки (30 минут — опционально)

### 7.1. Создай файл

- [ ] В репо инфраструктурщика — `recurring-tasks.md` (шаблон в `templates/recurring-tasks.template.md`).
- [ ] Добавь 1-3 первые задачи (мониторинг нагрузки API, проверка GitHub-бэкапов).

### 7.2. Правило в CLAUDE.md

- [ ] Добавь раздел «Регулярные проверки» (шаблон в `templates/recurring-rules.template.md`).

---

## Этап 8. Тест системы (30 минут)

### 8.1. Полный цикл

- [ ] Перезапусти все вкладки ассистентов (чтобы они подхватили актуальные правила).
- [ ] У одного ассистента дай команду через канал к другому. Проверь, что сообщение записалось.
- [ ] У другого ассистента напиши любое сообщение. Проверь, что он упомянул запись.
- [ ] У координатора дай команду «в планер: тест» (если есть API). Проверь, что задача появилась в сервисе.
- [ ] Отметь её выполненной в сервисе.
- [ ] Жди 60+ минут, заходи к координатору, пиши любое сообщение. Должно упомянуть «отмечено выполненным: тест».

### 8.2. Очистка

- [ ] Удали все тестовые записи в файлах каналов.
- [ ] Удали тестовые задачи в планировщике.
